# 服务器数据备份决策

本文件讨论持续数据保护，不替代 Git 中的 NixOS/SOPS 配置备份。迁移前生成的 `.age`
归档只是一份时间点恢复材料；持续备份必须有加密、保留策略、可观测性和恢复演练。

## 先分清三类内容

| 类别 | 示例 | 保护方式 |
| --- | --- | --- |
| 声明配置与密钥 | Flake、SOPS 密文、文档 | Git 私有仓库 + 至少一份独立 clone；Age 恢复私钥异地保存 |
| 结构化状态 | Vaultwarden、MySQL、PostgreSQL、MongoDB、Redis、Navidrome 数据库 | 先生成一致性逻辑导出，再备份导出与少量服务状态 |
| 大文件与对象 | RustFS 对象、OpenList 本地数据、音乐库、附件 | 块级/文件级增量备份；按重要性决定是否全量异地复制 |

不要仅打包 `/var/lib` 来代替数据库导出；也不要只保留数据库导出而忽略附件、对象和
应用元数据。恢复演练必须同时验证“数据库 + 对象/附件 + 服务配置”。

## 已落地：Hopper 本地 Restic + R2 快照复制

Hopper 当前已按以下方式部署：应用数据和一致性数据库导出先进入 Hopper 本地的专属
Restic 仓库，再用 `restic copy` 复制到专属 Cloudflare R2 仓库。首次本地快照、R2 复制、
R2 抽样完整性检查以及一次受控数据库恢复演练均已通过。具体操作见
[Hopper Restic 备份运行手册](./hopper-restic.md)。

`conduit` 已开始每日主动备份；`repeater` 已完成一份从 R2 实际还原验证过的迁移快照。
后者在其完整 NixOS 源码收编前不应被误认为持续备份。

不要用 `restic backup /var/lib/restic` 将一个 Restic 仓库嵌套备份到另一个仓库；应使用
`restic copy`，让快照、索引和保留策略按 Restic 的仓库语义复制。

## 方案 A：Restic 直连 Cloudflare R2

每台服务器用独立的 R2 前缀或独立 bucket，例如 `backups/hopper`、
`backups/repeater`。Restic 在上传前加密、去重和建立快照；NixOS 定时服务负责导出
数据库、执行备份、执行保留清理并将失败通知到 Telegram。

优点：无需自建备份服务器；恢复可从任意持有仓库密码和 R2 最小权限凭据的机器完成；
适合数据库、小文件和中等规模附件。缺点：R2 不是不可篡改存储，拿到同一组凭据的人
可以删除快照，因此仍应保留第二副本或离线副本。

建议保留：7 个日快照、4 个周快照、12 个月快照、2 个年快照。大音乐库与 RustFS
对象应单独设策略，避免日常小备份被首次全量传输拖垮。

## 方案 B：Restic 到 R2 + 第二异地副本（推荐的长期方案）

方案 A 作为主仓库，再将快照复制到另一家对象存储、家中 NAS 或离线硬盘。第二副本
使用另一套凭据和另一份仓库密码，避免云账号误操作或凭据泄漏同时毁掉两份数据。

优点：符合 3-2-1；恢复选择更多。缺点：成本、首次上传和运维复杂度更高。对于
Vaultwarden、数据库、照片/附件和重要 RustFS bucket，值得采用。

## 方案 C：Restic 经 OpenList WebDAV 写入网盘

可行，但应作为兼容网盘或第二副本：Restic 仍是负责加密、快照和保留的工具，OpenList
只提供 WebDAV 到网盘的传输层。不要把 OpenList 面板本身当备份系统。

优点：可使用已有网盘账号和现有 OpenList；缺点：WebDAV 驱动的重命名、列举、限流和
大文件稳定性由下游网盘决定，故障定位与恢复速度通常不如直接 S3。应先用一个小型
测试仓库连续跑一周，再承载 Vaultwarden 或数据库。

## 方案 D：Borg/Restic 到自有 NAS 或另一台独立服务器

使用 SSH/SFTP 或 Borg 服务把备份送到家中 NAS、独立存储机，或不承载业务的云主机。
不要将 Hopper 的业务数据只备份到 Hopper 自己的 RustFS，也不要把某台机器仅备份到
同一云厂商同一账号的另一块盘。

优点：长期容量成本可控、恢复速度快；缺点：需要维护一台真正独立且长期在线的存储端。

## 方案 E：云盘快照 + 逻辑备份

保留云厂商的启动卷/磁盘快照，用于整机快速回退；同时采用 A、B、C 或 D 之一保存
逻辑数据库导出与应用数据。快照不能替代逻辑备份：数据库在线写入和跨盘服务未必形成
一致恢复点，也不方便迁移到别家云。

## 各主机建议

| 主机 | 首先要保护的内容 | 建议频率 |
| --- | --- | --- |
| `hopper` | 四类数据库导出、OpenList/Aria2、Navidrome、RustFS 元数据与对象、Hermes 工作区 | 数据库每日；对象与音乐按变更量每日或每周 |
| `repeater` | Vaultwarden 数据库与附件、EasyTier、反代配置、Komari | Vaultwarden 每日；配置每日 |
| `conduit` | SOPS/Git、Xray/订阅相关运行状态、SSH host key | 每周或配置变更后 |
| `target` | 待盘点后决定 | 收编时确定 |
| `gcp-free` | SOPS/Git、Xray 与 EasyTier 状态 | 恢复连接后每周 |

## 任何方案都必须完成的验证

1. 首次备份后执行仓库完整性检查；
2. 每月至少恢复一次到临时目录或临时数据库，不覆盖生产数据；
3. 校验 Vaultwarden 附件、数据库导出、RustFS 对象清单和 Navidrome 数据库可读；
4. 备份失败必须通知 Telegram；
5. 将备份仓库密码和 Age 恢复私钥分别保存在两个独立位置。

## 决策建议

如果你希望最少维护：先选 **方案 A**，为 R2 单独创建仅限备份 bucket 的凭据；
如果 Vaultwarden、照片或 RustFS 数据不可丢：直接选 **方案 B**；如果优先利用网盘：
先用 **方案 C** 做非关键数据的试运行，再决定是否承载关键数据。
